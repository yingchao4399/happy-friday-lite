# Friday Preview.22 研究方案与验证计划

**阶段**：问题研究与设计冻结

**目标**：在任何代码修复、构建和发布前，建立可重复的证据链，证明 Office、会话历史、浮动助手和 Typewriter 的真实根因，并为下一阶段提供可执行的技术门禁。

**原则**：先证据、后设计、再实现；先修复协议边界，再修复界面；所有“已连接”“已恢复”“已完成”都必须由请求、存储、UI 和安装版四层证据共同证明。

---

## 1. 研究问题

### RQ-01：Office 422 是哪一层产生的？

需要回答：

1. renderer 发给主进程的 AgentMessage 是否包含完整的 `tool_calls`、工具 ID 和工具输出；
2. AI Core `executeCapability()` 在 schema 校验后是否保留这些字段；
3. provider 最终序列化的 JSON 是否满足 DeepSeek 的消息顺序和 ID 约束；
4. 失败是稳定的 4xx 参数错误，还是偶发网络/代理错误；
5. Docs、Sheets、Slides、PDF 是否共用同一根因。

### RQ-02：DeepSeek thinking 是否是独立失败条件？

需要回答：

1. `deepseek-flash` 当前默认 thinking 行为；
2. 工具调用后的 assistant 是否必须携带 `reasoning_content`；
3. Office bridge 和 AgentLoop 是否能完整保存/恢复 reasoning；
4. 若不能，Office 是否必须固定 `thinking: { type: 'disabled' }`；
5. `deepseek-reasoner` 或自定义 DeepSeek endpoint 是否需要独立策略。

### RQ-03：六类历史如何形成统一体验而不破坏各自资源边界？

需要回答：

1. 哪些入口已经以 `sessions/messages` 为事实源；
2. Office ProjectStore 的 `projectId/chatId` 如何与文件路径、重命名和临时文件绑定；
3. 日程、笔记、知识库普通/Agent、Dock 的 `scope/scopeKey` 是否稳定；
4. 历史列表、选择、加载、续聊和新建是否会出现竞态；
5. 统一悬浮历史面板的定位是否能脱离父级 overflow 和 WebContentsView 边界。

### RQ-04：Typewriter 卡顿和图片问题是否必须重做编辑模型？

需要回答：

1. 长文输入 P50/P95 的事件到绘制延迟；
2. 图片插入后哪些路径触发全量 Markdown 扫描或 DOM 重建；
3. textarea 是否能在保留原快捷键的同时承载图片节点；
4. 图片宽度、对齐和纸张融合状态应存在哪一层；
5. canvas 光照与 DOM 图片层组合时的合成成本和无障碍行为。

### RQ-05：Typewriter 的组件加载策略和 Dock 按钮合同是否统一？

需要回答：

1. Typewriter 首屏编辑所需的核心组件集合是什么，哪些必须在进入页面前完成加载；
2. 正文编辑器、图片节点、工具栏、预览、光照层和导出适配器的加载顺序是否会造成空壳、布局跳变或重复渲染；
3. “尽量一次性加载”在首屏可交互时间、内存、包体和低端设备上的边界是什么；
4. Dock 的“新建对话”和“会话历史”是否与其他入口使用同一按钮组件、scope 参数、焦点和无障碍合同；
5. 点击 Dock 两个按钮后，是否分别执行 `create(scope)` 和 `openHistory(scope)`，并且不会复用旧会话或触发错误面板。

### 2.2 运行证据

每次实验保存：

- 脱敏后的请求 envelope（消息正文用 hash 或长度替代）；
- provider 状态码、`type/code/param`、request ID 和阶段；
- renderer 事件时间线（send、tool-call、tool-result、done/error）；

- 性能 trace、内存峰值、长任务期间的 dropped frame 数。

正文、API Key、完整本地路径和私密文件内容不得进入共享报告。

## 3. 分阶段研究计划

### Phase 0：基线冻结和最小复现（0.5 天）

**动作**：

1. 清理临时修改，确认 `git status` 干净；
2. 创建隔离 userData 和测试模型配置；
3. 用固定的 Docs、Sheets、Slides、PDF 夹具复现一次单轮和一次工具轮；
4. 记录每个请求的消息数量、角色序列和字段集合；
5. 记录历史和 Typewriter 当前行为的截图与短视频。

**退出条件**：每个问题至少有一个可重复脚本或人工步骤，失败不依赖随机等待。

### Phase 1：Office 协议逐层取证（1 天）

#### 实验 1A：边界字段保留

构造包含以下消息的最小输入：

```json
[
  {"role":"system","content":"s"},
  {"role":"user","content":"u"},
  {"role":"assistant","content":null,"tool_calls":[{"id":"call_1","type":"function","function":{"name":"x","arguments":"{}"}}]},
  {"role":"tool","tool_call_id":"call_1","content":"r"}
]
```

在 `toOpenAiMessages()`、`executeCapability()` 入参、Zod `safeParse()` 输出、`ctx.chat()` 入参和最终 `JSON.stringify(body)` 五个位置分别抓取字段集合。

**预期研究结论**：如果只有 schema 输出丢字段，根因可归因到 AI Core 边界；如果更早丢字段，继续向 renderer/bridge 追踪。

#### 实验 1B：HTTP 状态矩阵

用本地 mock provider 返回 200、401、403、422、429、500、连接拒绝、超时和断流，检查：

- 是否重试；
- 是否保留响应状态；
- renderer 文案是否准确；
- 日志是否带 provider code/param 但不带正文；
- 已输出 token 或工具执行后是否错误重放。

**门禁**：422、401、403 禁止被归类为 `network`；429/5xx 才允许进入有限重试路径。

#### 实验 1C：DeepSeek thinking

针对 `deepseek-flash`、`deepseek-v4-pro`、`deepseek-reasoner` 和自定义模型：

- 请求体分别带/不带 `thinking`；
- assistant 是否携带 `reasoning_content`；
- 工具续轮是否被服务端接受；
- 新 run 恢复历史时是否还能取回 reasoning。

**决策**：如果 transcript 不能可靠保存 reasoning，则 Office 默认非 thinking；允许 reasoner 的条件必须写进 provider contract 和测试。

### Phase 2：会话事实源与历史交互（1 天）

建立六类入口的会话台账：

| 入口 | scope | scopeKey | 事实源 | 当前加载方法 | 目标资源隔离 |
| --- | --- | --- | --- | --- | --- |
| 主对话 | `friday` | 可为空 | SQLite sessions/messages | Friday history drawer | 用户主空间 |
| Office Docs/Sheets/Slides/PDF | 文件 ProjectStore | project/file | vendor JSONL + file map | Office history popover | 当前文件 |
| 笔记 | `note-agent` | `note:<id>` | SQLite sessions/messages | NoteEditor + ScopedHistoryButton | 当前笔记 |
| 知识库普通 | `knowledge` | `kb:<id>`/folder | SQLite sessions/messages | KbChatDialog | 当前库/目录 |
| 知识库 Agent | `knowledge-agent` | folder | SQLite sessions/messages + agent thread | KbAgentChatDialog | 当前目录 |
| 日程 | `schedule-agent` | 全局或日程范围 | SQLite sessions/messages | FridayAssistant | 日程空间 |
| Dock | `friday-dock` | null | SQLite sessions/messages | GlobalAgentDock | 全局助手 |

#### 实验 2A：选择竞态

快速连续点击 A、B、C 三条历史，注入不同延迟，验证最后点击的 C 必须胜出；旧消息、旧模型和旧 request 不得覆盖 C。

#### 实验 2B：新建与续聊

每个 scope 创建两条会话：新建后发送两条消息，切换旧会话继续发送，再重启应用；核对 session ID、消息顺序和标题。

#### 实验 2C：资源隔离和迁移

同名文件、文件重命名、临时文件保存、笔记复制、知识库切换、Dock/主对话交叉访问，检查列表是否串范围；记录旧数据迁移前后 session/message 数量。

**门禁**：所有入口的创建、选择、恢复、续聊、搜索、空态和新建都必须通过同一行为契约，视觉可以按原版适配。

### Phase 3：浮层、焦点和 Office overlay（0.5 天）

#### 实验 3A：定位和裁剪

在 100%、125%、150% DPI，窗口 1024/1366/1920 宽度，Office 左/右 AI panel，窄窗口和深色主题下，打开历史弹层并记录：

- `getBoundingClientRect()`；
- `z-index` 关系；
- 是否被父级 `overflow` 裁剪；
- 是否覆盖输入框、Ribbon 或正文；
- Escape、点击外部、Tab 焦点是否正确。

#### 实验 3B：拖动和展开性能

拖动 Dock 触发器、标题栏和 Office overlay 50 次，记录 pointer event 到位置更新延迟、IPC 次数、主窗口 bounds 变化和输入丢失。展开/关闭 50 次，记录首帧、稳定帧和编辑器输入阻塞时间。

同时逐一核对 Dock 的“新建对话”和“会话历史”按钮：在收起态、展开态、无历史、加载中、发送中、错误态和键盘导航下，记录按钮是否存在、可见区域、焦点顺序、scope、点击后路由和会话 ID。

**门禁**：浮层统一通过 body-level portal/overlay layer 定位；不能由 Office WebContentsView 内部的 overflow 决定可见范围；展开期间编辑器输入不丢失；Dock 两个按钮必须使用统一按钮合同，不能由 Dock 自定义一套语义。

### Phase 4：Typewriter 性能与图片模型（1-2 天）

#### 实验 4A：输入性能基线

准备 1k、10k、20k、50k、100k 字符，中文/英文/混合、软换行开关、普通/低 GPU、声音开/关，测量：

- keydown/input 到 textarea value 更新；
- input 到光标绘制完成；
- 输入到草稿日志写入；
- 预览切换到可交互；
- 长文滚动 P95/max frame time；
- JS heap、canvas 数量和图片解码峰值。

#### 实验 4B：图片全链路

测试 data URL、`file://`、`friday-asset://`、大图、透明 PNG、中文文件名、多图、失效资源、保存重开和跨笔记切换。记录 URL、显示位置、尺寸、失败回退和安全校验。

#### 实验 4C：编辑模型可行性

比较三种方案：

1. textarea + 绝对定位图片 overlay；
2. contenteditable + 自定义图片节点；
3. ProseMirror/Tiptap 文档模型 + Markdown 双向转换。

按输入延迟、撤销、IME、链接、选区、无障碍、兼容原 Markdown 和开发维护成本评分。只有能保存图片尺寸/位置并在重开恢复的方案可进入实现。

**门禁**：图片必须成为正文文档的一部分；不能只增加一个新的顶部预览条。

#### 实验 4D：Typewriter 组件加载与预热

建立三组对照：全部核心组件首屏加载、编辑器壳首屏加载后其余组件懒加载、核心组件首屏加载并对图片/导出资源后台预热。分别在冷启动、热启动、低速磁盘、100%/150% DPI 和低 GPU 设备记录：首屏可交互时间、首个光标出现时间、工具栏稳定时间、图片节点首次可用时间、布局跳变次数、JS heap 和首次输入延迟。

“尽量一次性加载”定义为：进入 Typewriter 后，编辑器壳、正文节点渲染器、输入/选区管理、核心工具栏、历史/保存状态在首屏完成加载并可交互；原图解码、导出适配器和非当前视口资源可后台预热，不得阻塞首屏。只有在首屏无空壳、无重复挂载、无明显布局跳变且性能阈值通过时，才允许采用该策略。

#### 实验 4E：打字滑块远距离定位与物理过渡动画

在底部滑块静止、缓慢移动和快速连续点击三种状态下，分别点击同一行近距离、跨行中距离和文档远距离位置。记录点击事件、目标 caret/scroll 位置、滑块当前视觉位置、动画起止时间、帧间位移、是否出现瞬移/回弹/追赶抖动，以及输入和滚动是否被阻塞。测试鼠标、触控板、键盘移动光标和 `prefers-reduced-motion` 四种路径。

设计验收：视觉滑块必须从当前实际渲染位置连续过渡到目标位置；新目标到达时从当前视觉位置重新规划，不把动画重置到旧起点；真实 caret、选区和文档滚动立即正确，滑块动画只负责反馈；启用减少动态效果时使用短时淡入/无位移动画，不违反系统设置。
### Phase 5：设置与真实 Agent 路由（0.5 天）

验证隐藏/显示、默认/简洁形象、Friday/Researcher/Auto、Agent 下拉选择在刷新和重启后保持；对每个选择发送请求，抓取实际 `agentId/agentMode/route`。如果后端没有真实路由，UI 必须显示“当前由 AI Core 自动调度”，并在 PRD 中标为未实现能力。

### Phase 6：综合回归与安装版门禁（1 天）

所有实现完成后才执行：

1. Node 单测、Office vendor 测试、Vite build；
2. Office Docs/Sheets/Slides/PDF 工具循环真实 probe；
3. 六类历史选择/新建/续聊/重启；
4. Dock 拖动、输入、历史、新建对话按钮、Office overlay；
5. Typewriter 核心组件一次性加载、长文、IME、声音、图片、重开；
6. Windows x64 安装、冷启动、升级/回滚/卸载；
7. SHA256、Git diff --check、包内资源审计；
8. GitHub push/release 只有在所有 P0/P1 门禁通过后执行。

## 4. 研究指标和通过阈值

| 指标 | 目标阈值 | 测量方式 |
| --- | --- | --- |
| Office 单轮首 token | P95 ≤ 3 秒（排除 provider 排队） | mock + 真模型各测 20 次 |
| Office 工具续轮 422 | 0/100 | 四类 Office 各 25 次 |
| 422 错误分类准确率 | 100% 显示参数错误/状态，不显示网络断开 | HTTP matrix |
| 历史选择竞态 | 100 次注入延迟均最后点击胜出 | fake IPC delay |
| 历史新建串会话 | 0 条交叉消息 | 六类各 10 组 |
| 浮层裁剪 | 0 次被父级 overflow 截断 | DPI/窗口矩阵 |
| Dock 展开输入阻塞 | P95 ≤ 100 ms，0 次丢字符 | performance trace |
| Dock 新建/历史按钮可见性 | 100% 状态可见，0 次错误 scope | 状态矩阵 + 可访问性检查 |
| Typewriter 首屏核心组件就绪 | 冷启动 P95 ≤ 1.5 s，0 次空壳/布局跳变 | Electron trace + 录屏 |
| Typewriter 首次输入 | 核心组件加载后首字符延迟 P95 ≤ 100 ms | IME/键盘 trace |
| Typewriter 打字滑块过渡 | 远距离点击 0 次瞬移/回弹；动画 P95 ≤ 300 ms，≥ 55fps | 帧时间线 + 录屏 |
| Typewriter 输入延迟 | 20k 字符 P95 ≤ 50 ms；50k P95 ≤ 100 ms | Playwright/Electron trace |
| Typewriter 预览切换 | 20k 字符 P95 ≤ 500 ms | 20 次切换 |
| 图片重开恢复 | URL、尺寸、对齐 100% 一致 | 多格式夹具 |
| 设置持久化 | 重启后 100% 一致 | 独立 userData |

阈值必须记录测试机器和模型，不得只报告平均值。

## 5. 风险、反证和回滚

### 5.1 可能推翻当前假设的证据

- 如果抓包显示 tool_call_id 在进入 `executeCapability()` 前已经丢失，需把根因前移到 renderer AgentLoop；
- 如果 provider 返回 422 的 param 不是 tool_call_id，需保留 schema 根因但补充另一个 payload 错误；
- 如果 Typewriter 输入瓶颈主要来自 GPU canvas 而不是文本/图片模型，需调整优化优先级；
- 如果 Office vendor history 已完整但只在安装包失效，需查资源打包或 preload 版本漂移。

### 5.2 回滚要求

- 每个实现阶段独立 commit；
- 先备份 userData 数据库和 Office ProjectStore；
- 会话迁移必须可重复、可校验、可回退；
- Typewriter 文档模型迁移必须保留原 Markdown 原文；
- 新版安装器不得覆盖旧安装目录，先使用隔离 userData 做升级/回滚验证。
