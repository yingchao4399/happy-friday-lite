# Office AI 工具调用连续失败根因调查报告

调查日期：2026-11-05（Asia/Shanghai）
调查对象：Happy Friday Lite Office PDF 助手
用户现象：面板显示 “Tool input was unusable (unparseable or truncated) 3 times in a row; retries stopped”
当前结论：这是 Office AI 工具调用协议在“模型流式输出 → Friday 主进程 bridge → renderer AgentLoop”边界上的问题，不是 PDF 文件损坏，也不是 PDF 转 Word 转换器报错。

## 1. 与此前 422 问题的区别

此前 Preview.22 的 422 问题是第二轮消息被 AI Core schema 删除 tool_calls/tool_call_id，服务端拒绝请求。该问题已经在 src-electron/agent/tools/builtin/aiChat.js 中改为保留完整 OpenAI-compatible 字段，并由 src-electron/ai-core/canonical-message.js 做白名单校验。

本次截图的文案完全不同：

- 没有 HTTP 状态码；
- 没有 provider/network 错误；
- 错误文字来自 vendor/happyoffice/packages/agent-core/src/loop.ts；
- 触发条件是连续 3 个 turn 的工具参数带 inputError 或 truncated。

因此，本次是模型已经返回了工具调用，但 Friday 在解析工具参数时判定 JSON 不可用。继续重试同一会话只能把同一个坏参数再次交给模型，达到 3 次后由 AgentLoop 停止。

## 2. 证据链

### 2.1 错误生成位置

vendor/happyoffice/packages/agent-core/src/loop.ts 中：

1. MAX_INPUT_PARSE_RETRIES = 3；
2. 工具调用带 call.inputError 或 call.truncated 时不执行工具；
3. 把错误结果回传给模型；
4. 连续 3 次仍不可解析时触发截图中的英文错误。

这说明截图中的失败发生在 renderer AgentLoop，而不是 PDF renderer 的页面读取函数或 PDFium。

### 2.2 Friday 实际使用的是自定义 Office bridge

Office 不直接使用 GenOffice 的 ai-provider OpenAI-compatible parser，而是经过：

PDF renderer AgentLoop
  → ai:stream IPC
  → src-electron/office/office-ai-bridge.js
  → executeCapability('ai_chat_inference')
  → fridayStreamRequest()
  → OpenAI-compatible /chat/completions

旧 bridge 的问题包括：

- 请求体没有发送 max_tokens，renderer 设置中的 8192 输出预算没有落到 provider 请求；
- delta.function.arguments 被无条件 append；
- 没有兼容 provider 重发的完整/累计 arguments；
- finish_reason=length/max_tokens 没有转换为 truncated=true；
- 解析错误只剩 inputError，模型无法区分“引号错误”和“输出被截断”。

GenOffice 的上游 parser 已经具备更完整的 finish reason、工具参数拼接和错误处理，但 Friday 的 Office 接管层绕开了这套实现，形成了第二套协议实现。

### 2.3 为什么 PDF 更容易触发

PDF 的 read_pages 工具单次最多读取 10 页，结果最多约 24,000 字符；这些结果会完整进入下一轮模型上下文。22 页文档通常需要多轮读取，导致：

- 请求上下文快速增大；
- 模型需要在长上下文中继续生成工具调用；
- 如果 provider 使用默认输出预算或流式中断，最后一个 JSON 参数可能只收到半截；
- 旧 bridge 又没有把 max_tokens 截断标记传回 AgentLoop，于是它被当作普通 JSON 解析错误反复重试。

截图中 PDF 页数为 22 页，与该放大条件一致，但问题本身是通用的，Docs/Sheets/Slides 也可能在大工具结果或复杂编辑操作时触发。

### 2.4 模型配置与网络状态

本机运行日志反复记录 Office 已选择 DeepSeek 模型和 API 地址，说明模型配置同步成功。截图错误也不是连接超时、401、429 或 5xx；如果是这些错误，bridge 会通过 errorCode 走 auth/network/overloaded 分支，不会进入 AgentLoop 的 inputParseFails 计数。

API Key 只存在于本机配置中，调查记录不保存其值。

## 3. 根因分层

| 优先级 | 根因 | 影响 |
| --- | --- | --- |
| P0 | Office bridge 是独立的简化工具参数解析器，与上游协议不一致 | 合法的累计 delta 可能被拼成非法 JSON |
| P0 | 未发送 max_tokens | 长 PDF 工具续轮更容易在参数 JSON 尚未闭合时结束 |
| P0 | 未把 length/max_tokens 标记为 truncated | AgentLoop 无法让模型采用“拆小调用”策略 |
| P1 | 工具结果较大且每轮重传 | 22 页 PDF 放大上下文压力 |
| P1 | 错误文案只显示“不可解析或截断” | 用户无法区分 provider 截断、模型输出错误和真正的引号问题 |
| P2 | bridge 与 GenOffice parser 双轨维护 | 上游修复无法自动进入 Friday，后续升级容易再次回归 |

此前的 422 schema 问题属于另一条 P0，当前代码已经有修复；不能把它和本次 inputParseFails 错误混为同一个故障。

## 4. 本轮已实施的协议修复

本工作区已增加 src-electron/office/office-ai-stream.js，并修改 src-electron/office/office-ai-bridge.js：

1. Office 请求固定带 8192 默认 max_tokens，同时允许模型配置提供 256～32768 范围内的值；
2. 工具名和 arguments 支持“片段式”和“累计完整值”两种 provider delta；
3. provider 返回 length/max_tokens 时，最后一个工具调用带 truncated=true；
4. 工具参数异常只记录工具名、长度、stop reason 等脱敏元数据，不记录完整参数或 PDF 内容；
5. 新增纯函数测试，覆盖累计参数、重复参数和截断工具调用。

## 6. 仍需进行的真实验收

Windows x64 候选安装包已经生成，但还没有在截图所示的同一份 22 页 PDF 和真实线上模型配置下完成端到端复现/回归。因此当前可确认“协议修复已进入安装包且本地验证通过”，不能据此宣称真实模型问题已彻底解决。

下一步验收必须固定以下证据：

1. 同一 22 页 PDF；
2. 同一模型配置；
3. 发送“先读取全文再回答”类请求；
4. 记录每个 turn 的工具名、参数长度、stop reason、是否 truncated（不记录正文）；
5. 证明不再出现连续 3 次 inputParseFails；
6. 再用 Docs、Sheets、Slides 各执行至少 10 轮只读工具续轮；
7. 在隔离 userData 中启动 preview.34 安装包复测，避免旧 bundle 或旧会话历史干扰。

## 7. 规划结论

这不是继续增加重试次数能解决的问题。短期发布应保留 Office 默认非 thinking 模式、固定输出上限、正确传递截断状态，并完成大 PDF 回归；中期应把 Friday Office bridge 改为复用 GenOffice 的统一 provider parser，或抽出双方共享的纯协议包，避免主进程再维护一套简化实现。只有这样，后续融合 v0.12.600 时，上游对工具流、usage、JSON 限制和 provider 兼容性的修复才不会再次被 Friday 接管层截断。
