# 3.0.6-preview.3 性能修复与验收

## 问题与修复

用户截图中 Friday 约占 2532MB，伴随高磁盘写入。实机只读检查发现，旧主进程私有内存超过 2GB。430575616 字节的备份中，122 次 PDF OCR 调用的审计参数累计约 406MB；8 篇笔记正文合计约 30KB。

1. 旧 sql.js 将整库加载进 WASM，保存时又导出整库并复制成 Buffer，再同步覆盖文件。改用 Electron 42 内置 node:sqlite 按页读写，页缓存上限 16MB，事务提交即持久化；保留业务 saveDb/flushDb 协议和旧 SQLite 文件格式。
2. 能力执行 finally 原先直接 JSON.stringify 图片、正文和工具返回值。现在在序列化前限制深度、节点、数组与字符串，隐藏敏感字段，UI 审计仅记录类型元数据；真实业务返回值和权限审批不改。历史日志查询也限制字段长度和条数。
3. 剪贴板修改一条原先删除并重插全部历史。现在仅 upsert 变化记录，并在同一事务更新对应标签。截图哈希直接处理图片字节，减少 base64 中间副本。
4. 主进程原先全局禁止 Chromium 后台限流，Office 隐藏视图也持续全速运行。移除全局禁止项，交互视图开启正常限流，打印/导出窗口继续由专用流程控制。
5. 应用内复制/剪切事件原先无人调用收录入口。主 preload、原生编辑菜单和键盘入口现已接通。自有编辑器菜单仍自行处理。
6. 在线备份先生成一致 SQLite 快照再压缩；升级快照目录核验在 worker 内完成，主进程不再为了检查目录而再次读取整个压缩包。已有零字节数据库停止初始化，保留原文件并显示恢复入口。

## 对照方法

- 官方源码提交：`54e89a6`，package.json 版本 `3.0.5`。该版本从本地 Git 归档为独立目录，没有把已安装的自定义 3.0.6 或 preview.2 误作官方原版。
- 两版使用同一 Electron 42.2.0、Windows 主机和依赖目录，加载各自生产前端和真实 main.js、Office 资源；数据目录、Chromium profile、数据库副本独立。
- 运行完整应用，测量首页、实际打开笔记、打开相同 DOCX、关闭 DOCX 四个阶段。每阶段取三个样本，三轮交替先后顺序，比较九个样本中位数。
- 统计主进程全部后代进程的 Windows PrivateMemorySize64 与 WorkingSet64，含被启动的 DSH；排除采样 PowerShell 及其后代。测试并未启用或调用真实模型，本次默认首页不启动 DSH。
- 第一组为完整 430575616 字节数据库副本。第二组保留相同业务数据和审计记录数，仅在隔离副本将审计正文改为摘要并 VACUUM，大小 2236416 字节，用于避免仅依赖历史冗余数据取得优势。
- 原用户程序保持运行；没有覆盖安装目录、真实数据库或模型配置。未模拟强制 GC、trim working set 或关闭功能。

## 结果

首次大库诊断统计包含采样子进程开销，只用于定位，不作为交付数字。以下区分不同阶段和统计口径。

保持业务数据相同的三轮完整应用对照（后续按需加载优化之前的源码结果），九个样本中位数，MB：

| 场景 | 官方私有提交 | 预览版私有提交 | 官方工作集总和 | 预览版工作集总和 |
| --- | ---: | ---: | ---: | ---: |
| 首页 | 551.5 | 463.2 | 676.7 | 612.2 |
| 打开笔记 | 495.6 | 443.3 | 629.4 | 599.5 |
| 打开 Word | 643.8 | 516.0 | 827.6 | 744.6 |
| 关闭 Word | 621.7 | 429.3 | 793.6 | 590.8 |

进一步延迟加载 Agent、DSH、RAG 与 Office 编辑器、缩小首页图片并优化脉冲动画后，最终 preview.3 打包目录启用原生剪贴板监听的一轮隔离实测：四个应用进程空闲私有物理内存为 116.9–118.3MB，私有提交为 244.5–246.0MB，全部工作集相加为 323.2–324.5MB。私有物理内存按 Windows WorkingSetPrivate 统计；工作集总和重复计算共享页。物理口径低于 200MB，私有提交口径尚未达到 200MB；不能混淆这两个结论，也不能用这一轮数字冒充三轮官方对照。

用户指定的 `红书_4.pdf` 为 18,234,244 字节、1042 页。源码副本实测：首屏 8824ms；第 15 页两字符选区与复制接口一致；连续滚动约 10 秒，P95 30.2ms、最大 73.2ms，没有超过 100ms 的帧，最多四个页面 Canvas。关闭后视图释放，原文件 SHA256 未变。PDF 逻辑还修复了自动 OCR 为了处理当前页先索引整本书的问题，当前只处理可见页并串行排队。这仍不能替代所有复杂版式的完整选区验收。

原官方 PDF 归档产物含无效的 macOS 绝对入口，带该 PDF 的官方对照未完成；该失败运行不计入通过结果。记录见 `business/summary.json`、`idle-packaged-clipboard.json` 和 `pdf-redbook-final.log`。

## preview.4 最终包复核（2026-10-25）

- 最终安装载荷：`release/preview4/win-unpacked`，版本 `3.0.6-preview.4`。
- 空闲三次采样：私有提交 240.4–243.4MB；私有物理工作集 100.4–102.5MB；全部工作集 375.1–377.3MB。私有物理工作集低于 200MB，私有提交仍高于 200MB，二者不能混称。
- 真实打开 Word 三次采样：私有提交 359.1–371.5MB；私有物理工作集 211.6–223.5MB。打开编辑器会加载渲染器、字体和文档 DOM，不能用空闲目标推断打开文档目标。
- 最终包外部剪切板/复制、Friday 历史自动刷新、历史复制回外部、原版笔记正文右键复制和重载持久化全部通过。
- 最终包《红书_4.pdf》二次复核：1042 页，首屏 8836ms，P95 36.1ms，最大 78.6ms，无超过 100ms 帧，最多 4 个页面画布；第 15 页两字符精确选区通过，关闭后视图销毁，原文件哈希未变。
- Office 主进程按需拆分：docs 2.06MB、sheets 2.11MB、slides 2.15MB、pdf 1.04MB；附件解析器 7.74MB 只在首次读取附件时加载；最近文件/收藏/重命名/删除共用轻量模块，不拉起 Word 引擎。
- 最终包原生依赖审计通过：DSH Harness、node-addon-require-builtin、三个 Windows PE helper 均通过。

## 功能回归

- SQLite 文件双向兼容、迁移幂等、事务回滚、小字段即时持久化、大字段增量写入。
- 巨大 OCR 图片、二进制、循环和访问器对象经过实际能力入口后，审计/事件有界，真实返回值与权限拒绝行为正确；历史大日志查询截断。
- 单条剪贴板修改不重写其他记录，标签和删除正确，失败时整体回滚。
- 备份过程中继续编辑，压缩内容为一致快照，新编辑在当前库重启后仍存在。
- 真实 Electron 键盘复制、剪切、正文右键菜单、菜单复制后进入历史通过。
- 已有空数据库不会被静默覆盖。

## 适用范围

这是上述四个工作负载的整应用内存比较，不代表所有文件、所有模型会话或任意规模数据均有相同降幅。大型 PDF、多文档重负载、用户长期连续操作和安装升级仍须分别验收。不能据此宣称原迭代计划的全部功能已经完成。
