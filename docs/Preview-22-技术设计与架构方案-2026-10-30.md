## 1. 设计结论

本次迭代采用“边界重建”的方案，不在现有 Office bridge、各页面局部历史组件和 Typewriter 顶部图片条上继续堆补丁。系统需要重新确立四个稳定边界：

1. **AI Core 协议边界**：任何消息进入 provider 前必须保留 OpenAI-compatible 消息所需的 `tool_calls`、`tool_call_id`、`name`、`reasoning_content` 等字段，并在 thinking 与 non-thinking 两种模式下使用明确的消息合同。
2. **会话数据边界**：所有入口通过统一 `ConversationStore` 读写会话，使用 `scope/scopeKey` 隔离主对话、Office 文件、笔记、知识库、日程和 Dock，UI 不再自行维护第二份历史事实源。
3. **浮层交互边界**：Office overlay、全局 Dock 和历史侧边栏全部挂载到统一 body-level overlay root，使用同一套定位、拖动、层级、焦点和安全区算法。
4. **富文档边界**：Typewriter 图片作为正文中的可持久化节点，复用笔记模块的正文锚点、宽度策略和渲染位置，支持小图默认尺寸、鼠标拖拽缩放、对齐与光照融合，删除顶部独立图片条。

这四个边界必须先由契约测试和观测数据证明，再进入 UI 优化和安装包发布。

## 2. 现状架构与根因映射

### 2.1 Office 请求链路

当前路径为：

```text
Office renderer
  -> office-ai-bridge.js
  -> ai_chat_inference capability
  -> executeCapability()
  -> builtin/aiChat.js Zod schema
  -> AgentLoop/provider adapter
  -> DeepSeek OpenAI-compatible endpoint
```

`aiChat.js` 使用只声明 `role`、`content` 的对象 schema。Zod 默认移除未知字段，造成两类协议损坏：

- assistant 消息的 `tool_calls` 被去掉，后续 tool 消息失去对应的调用上下文；
- tool 消息的 `tool_call_id` 被去掉，DeepSeek 无法将工具结果绑定到调用。

本机日志已出现 `messages[3]: missing field tool_call_id`，这属于确定性的 HTTP 422 参数错误，不应继续被包装成“网络有问题”。此外，DeepSeek Flash/V4 thinking 工具续轮可能要求 assistant 的 `reasoning_content`，现有 Office transcript 与 AgentLoop 没有稳定保存和回传该字段，故只保留 ID 仍不够。

### 2.2 会话历史

当前存在 Friday SQLite、Office ProjectStore、组件内临时数组等多套事实源。会话选择动作有时只切换 UI 状态，不重新加载完整消息；不同页面的 `scope` 也没有统一定义，导致历史串台、缺少新建按钮、恢复后丢上下文。

### 2.3 浮层与 Dock

Office overlay 和 Dock 使用不同坐标系、不同窗口层级与事件转发规则。部分路径使用固定右下角布局，部分路径使用 renderer 内的 absolute 定位；拖动时坐标转换、DPI 缩放和边界约束不一致。输入框的 focus、pointer capture、IPC 发送和当前会话状态没有组成一个单一状态机。

### 2.4 Typewriter 图片

Typewriter 仍以 textarea/Markdown 文本为主要编辑状态，图片通过扫描或 `typewriter-image-strip` 显示在正文上方；图片没有正文节点 ID、锚点、尺寸、对齐、光照元数据，也没有和笔记模块共享渲染器。因此图片位置、缩放和持久化都无法满足用户要求。

## 3. AI Core 协议设计

### 3.1 Canonical transcript

新增内部类型 `CanonicalMessage`，作为 Office、主对话、Dock 和所有 agent 的唯一中间格式：

```ts
type CanonicalMessage = {
  id: string;
  role: 'system' | 'user' | 'assistant' | 'tool';
  content: string | ContentPart[] | null;
  name?: string;
  tool_calls?: ToolCall[];
  tool_call_id?: string;
  reasoning_content?: string;
  providerMetadata?: {
    provider: string;
    model: string;
    requestId?: string;
  };
  createdAt: number;
};

type ToolCall = {
  id: string;
  type: 'function';
  function: { name: string; arguments: string };
};
```

`CanonicalMessage` 进入 provider adapter 前必须通过完整性校验：

- assistant 带 `tool_calls` 时，每个 tool call 必须有稳定 ID、函数名和可解析的 arguments；
- role 为 tool 时必须有 `tool_call_id`，并且 ID 必须存在于上一条 assistant 的 tool_calls；
- tool 消息不能被压缩成普通 assistant 文本；
- `reasoning_content` 仅在 provider 支持、且当前请求启用 thinking 时透传；
- 不允许 provider adapter 自行猜测缺失字段，缺失时返回结构化 `TRANSCRIPT_INVALID`。

### 3.2 能力 schema

`ai_chat_inference` 的私有能力 schema 使用 `.passthrough()` 或显式完整消息 schema，禁止默认 strip：

```ts
const messageSchema = z.object({
  role: z.enum(['system', 'user', 'assistant', 'tool']),
  content: z.union([z.string(), z.array(contentPartSchema), z.null()]),
  name: z.string().optional(),
  tool_calls: z.array(toolCallSchema).optional(),
  tool_call_id: z.string().optional(),
  reasoning_content: z.string().optional(),
}).passthrough();
```

`.passthrough()` 仅用于保留未来 provider 扩展字段，发送前仍必须执行白名单序列化和敏感字段清理。公共能力输入、日志和用户可见错误不得泄漏密钥、完整 prompt 或文件内容。

### 3.3 thinking 策略

对 DeepSeek Flash/V4 建立显式策略：

- `thinking: disabled`：Office 默认模式，工具续轮不依赖 reasoning 字段；适合编辑、格式化、文件操作等高频操作。
- `thinking: enabled`：仅当 provider 能力声明支持、transcript 能保存和恢复 `reasoning_content`、且测试矩阵通过时开放。
- thinking 状态不能由 UI 文字推断，必须由 resolved provider config 记录到请求审计事件。
- 若 thinking 续轮数据缺失，返回 `THINKING_TRANSCRIPT_INCOMPLETE`，由 UI 给出“当前模式无法继续本轮工具调用，请新建会话或切换兼容模式”的可行动提示。

### 3.4 结构化错误合同

所有 provider 错误统一为：

```ts
type AiError = {
  kind: 'provider_request' | 'transcript' | 'network' | 'auth' | 'capability';
  code: string;
  message: string;
  httpStatus?: number;
  providerCode?: string;
  requestId?: string;
  retryable: boolean;
  safeDetails?: Record<string, string | number | boolean>;
};
```

HTTP 422 必须保留 status、provider code、request ID 和参数路径（例如 `messages[3].tool_call_id`），但对用户显示简化后的中文说明；“检查网络”只允许在 `kind=network` 时出现。日志记录脱敏后的 transcript 摘要和字段存在性，不记录完整敏感内容。

### 3.5 协议观测

每轮请求写入 `ai.request.started`、`ai.request.serialized`、`ai.request.completed/failed` 三类事件，字段包括 provider、model、thinking、messageCount、toolCallCount、hasReasoning、httpStatus、requestId、scope。事件必须可按 conversationId 关联，但不得保存 API key 或完整文档内容。

## 4. 统一会话存储

### 4.1 ConversationStore 接口

```ts
interface ConversationStore {
  list(scope: ConversationScope, query?: HistoryQuery): Promise<ConversationSummary[]>;
  create(input: CreateConversationInput): Promise<ConversationSummary>;
  load(id: string): Promise<ConversationAggregate>;
  appendMessage(id: string, message: CanonicalMessage): Promise<void>;
  rename(id: string, title: string): Promise<void>;
  archive(id: string): Promise<void>;
  delete(id: string): Promise<void>;
  migrate(source: LegacySource): Promise<MigrationReport>;
}

type ConversationScope = {
  scope: 'main' | 'office' | 'note' | 'knowledge' | 'schedule' | 'dock';
  scopeKey?: string; // fileId、noteId、kbId、scheduleId；main/dock 可为空
  ownerId?: string;
};
```

所有入口的历史侧边栏调用同一套 `list/load/create`。页面只负责传入 scope 和 scopeKey；不得直接读取另一模块的 SQLite 表、ProjectStore 或组件缓存。

### 4.2 资源隔离规则

- Office：`scope=office, scopeKey=fileId`，同一文件的历史可跨 Docs/Sheets/Slides/PDF 共享，但不同文件绝不串台。
- 笔记：`scope=note, scopeKey=noteId`。
- 知识库：`scope=knowledge, scopeKey=kbId`，普通对话和 Agent 对话通过 `mode` 字段区分。
- 日程：`scope=schedule, scopeKey=calendarId/eventId`。
- Dock：默认 `scope=dock, scopeKey=global`，从 Dock 跳入上下文页面时可复制为目标 scope 的关联会话。
- 主对话：`scope=main, scopeKey=global`。

### 4.3 历史选择竞态

每个侧边栏维护 `selectionEpoch`：发起 load 时记录 epoch，返回时若 epoch 已变化则丢弃旧响应。新建会话先写入 store，再更新 UI；消息流式追加以 conversationId 为键，不允许依据“当前选中项”猜测写入目标。

### 4.4 迁移与回滚

迁移分为发现、影子写入、校验、切换四阶段。旧表和 ProjectStore 保留只读回退窗口；每条迁移记录保存 sourceId、targetId、messageCount、hash、失败原因。若校验失败，入口回退到 legacy adapter 并上报 `MIGRATION_MISMATCH`，不能静默丢消息。

## 5. 统一悬浮侧边栏与 Dock

### 5.1 Overlay root

应用启动时创建单一 `#friday-overlay-root`，所有历史侧边栏、Office assistant panel、Dock expanded panel 和 modal 均挂载其下。层级由 token 管理：

```text
base content: 0
context overlay: 1000
history panel: 1100
assistant panel: 1200
dialog/modal: 1300
toast: 1400
```

禁止使用跨模块的任意 `z-index: 99999`。overlay root 读取窗口尺寸、safe-area、DPI 和当前可见区域，统一计算 left/top/right/bottom。

### 5.2 定位与拖动

Dock 收起态和展开态共享同一个 `DockPosition {anchor, x, y}`，展开仅改变面板尺寸。拖动开始时使用 pointer capture；坐标统一转换为 CSS 像素；边界为可视区域减去面板尺寸、16px 安全边距和当前系统缩放后的 dock margin。窗口 resize、DPI 变化和多显示器切换时重新 clamp。

Office overlay 不再通过独立主进程固定坐标移动；renderer overlay manager 负责定位，主进程只提供窗口和显示器几何信息。这样可消除 Office 中被侧边栏边缘遮挡、拖动跳点和展开后不可见的问题。

### 5.3 输入状态机

Dock 和所有助手面板复用 `AssistantComposer`：

```text
idle -> focused -> composing -> submitting -> streaming -> idle
                                  \-> failed -> composing
```

发送前锁定 conversationId 和 provider config；输入框使用 compositionstart/compositionend 兼容中文输入；提交期间保留草稿和取消按钮；流结束后只追加一次 assistant message。点击历史项、切换窗口或拖动 Dock 不得抢走 composing 状态，除非用户明确点击输入框外并触发 blur。

### 5.4 Dock 设置与 Agent 语义

设置中的“Friday 显示/隐藏”只控制全局 Dock 的可见性；“形象设置”只改变 avatar/主题资源；“分身模式”必须映射到明确的 agent profile 和工具权限；“agent 切换”必须写入当前 conversation 的 agentId，并在下一轮请求审计中可见。不可只保存一个 UI 开关而继续使用旧 agent。

### 5.5 统一按钮合同：Dock 新建与历史

Dock 必须复用各模块使用的 `NewConversationButton` 和 `HistoryButton`（实际命名以代码基线为准），或抽象出等价的共享组件。按钮合同包含：

- 固定的 icon、label、尺寸、圆角、间距和 hover/pressed/disabled/focus 状态；
- `scope`、`scopeKey`、当前 `conversationId` 和 `agentId` 显式传入，不从全局单例猜测；
- 新建按钮调用 `ConversationStore.create()`，成功后切换到新 conversationId；
- 历史按钮调用统一 `openHistory({scope, scopeKey})`，打开同一悬浮侧边栏并加载当前 scope；
- 无历史、加载中、发送中、错误和键盘导航状态均有明确可见反馈；
- 具备相同的 `aria-label`、键盘顺序和点击热区。

Dock 不得使用只改变图标、只打开旧数组或只触发展开动画的伪按钮。验收时必须证明两个按钮在 Dock、主对话、Office、笔记、知识库和日程中视觉与语义一致。

## 6. Typewriter 富文档与图片模型

### 6.1 正文节点模型

Typewriter 文档从纯 Markdown 字符串扩展为可迁移的 block/inline 文档模型。图片节点示例：

```ts
type ImageBlock = {
  id: string;
  type: 'image';
  assetId: string;
  anchor: { blockId: string; offset: number };
  width: number; // CSS px，默认 160
  height?: number;
  align: 'left' | 'center' | 'right' | 'inline';
  fit: 'contain' | 'cover';
  light: { intensity: number; temperature: number; shadow: number; blend: 'paper' | 'photo' };
  alt?: string;
};
```

图片必须插入正文编辑器的真实节点树，使用与笔记模块相同的 anchor 规则、内容宽度、段间距和光照上下文。**验收要求是图片与笔记模块正文图片处在同一类位置和流式排版中**：不能渲染到顶部 `typewriter-image-strip`，不能另起一个脱离正文的图片区域。

### 6.2 尺寸和交互

默认插入为小图（160px 长边，受正文宽度约束）。选中图片显示四角/边中控制点；拖动时保持最小 96px、最大为正文可用宽度，支持 Shift 保持比例。尺寸、对齐和光照滑块在 pointerup 或节流间隔内写入文档状态，并支持撤销/重做。

### 6.3 图片安全协议

本地资源统一通过 `friday-asset://assetId` 读取，renderer 不接受任意 `file://` 或未经校验的远程 URL。主进程检查 assetId 所属工作区、MIME、大小和访问权限；渲染失败显示可恢复占位节点，不阻塞整篇文档。

### 6.4 光照融合

编辑器根据纸张材质 token 计算图片混合：默认使用 paper blend，提供强度、色温、阴影三个受限参数。光照效果只作用于图片节点的渲染层，不修改原始 asset；导出时使用同一套 CSS/Canvas 参数，保证预览和导出一致。

### 6.5 性能策略

- 文档状态使用增量 patch，禁止每次按键重新序列化整篇 Markdown；
- 预览和图片节点按可视区域虚拟化，保留当前视口前后各一个屏幕的缓冲；
- 输入事件与持久化解耦，编辑态只更新局部节点；
- 图片缩略图、原图和纹理缓存分层；
- 流式 AI 输出通过批量帧更新，目标 30–60fps，避免每个 token 触发全树重渲染。

### 6.6 组件加载与预热边界

Typewriter 采用“核心组件首屏就绪、重资源后台预热”的加载策略：

1. 首屏同步/并行加载编辑器壳、正文节点渲染器、输入与选区管理、核心工具栏、保存状态、图片节点控制器和历史入口；用户进入页面后不应看到只有纸张外壳而没有工具栏或输入能力的中间态。
2. 图片原图解码、非当前视口纹理、导出适配器和低频设置面板可以在首屏后预取，但必须提前注册组件边界，避免首次交互时重新挂载整棵编辑器树。
3. 用 `Promise.all`/资源清单或等价的预加载控制统一记录加载阶段；组件加载失败只降级对应能力，不阻塞正文输入。
4. 预热不能以牺牲首屏性能为代价：加载策略必须以冷启动可交互时间、JS heap、首个输入延迟和布局跳变次数作为门禁。
5. Typewriter 的图片节点、工具栏和预览使用同一文档状态，禁止分别维护一套延迟加载的图片列表。

这里的“一次性加载”指核心编辑体验在首屏一次完成，不要求立即解码所有原图或把所有导出库强行塞入首屏；具体边界由研究方案中的 4D 实验和真实设备指标确定。

### 6.7 打字滑块的物理过渡模型

底部打字滑块必须与真实编辑状态解耦：

```ts
type CaretIndicatorState = {
  visual: { x: number; y: number; width: number; opacity: number };
  target: { x: number; y: number; width: number; opacity: number };
  animationToken: number;
  reducedMotion: boolean;
};
```

点击远处文字后，编辑器先同步设置真实 selection/caret 和滚动目标，再读取稳定的 caret rect 作为 `target`。滑块从当前已经绘制的 `visual` 位置启动连续过渡，不能从旧的逻辑位置或默认位置重新开始。实现可采用 Web Animations API、CSS transform + compositor 或等价的 requestAnimationFrame spring，但必须满足：

- 使用 `transform: translate3d()` 等合成属性，避免每帧触发整篇正文重排；
- 近距离点击使用短时 ease-out，远距离点击使用受限的平滑 spring/ease 曲线，最大时长 300ms；
- 动画中再次点击时取消旧 animation，并以当前视觉坐标作为新起点，避免跳回、回弹和速度突变；
- 点击、键盘移动和滚动导致的目标变化走同一状态机，不能分别实现三套滑块逻辑；
- `prefers-reduced-motion: reduce` 时关闭位移或缩短为不超过 100ms 的淡入，不能影响 caret 正确性；
- 动画只改变视觉指示器，不延迟真实输入、选区、撤销或保存。

性能门禁为远距离点击动画无可见瞬移和回弹，动画期间帧率 ≥55fps，且不产生超过 50ms 的主线程长任务。
## 7. 测试与发布门禁

### 7.1 必须通过的契约测试

1. Office 工具续轮 JSON 中 assistant `tool_calls` 和 tool `tool_call_id` 完整存在；
2. DeepSeek 422 参数矩阵在 thinking disabled/enabled 下给出预期结果；
3. 所有 scope 的 create/list/load/append/rename/archive/delete 可重复执行且无串台；
4. 历史快速连续点击时旧响应不会覆盖新选择；
5. Dock 在 100%、125%、150% DPI 和多显示器边界可拖动、可输入、可发送；
6. Dock 的新建对话和会话历史按钮在所有状态下可见、可聚焦，并且 scope 与其他入口一致；
7. Office overlay、Dock、笔记、知识库、日程均使用同一悬浮侧边栏和新建按钮；
8. Typewriter 图片在正文锚点显示，默认小图、可缩放、可保存、重开后位置和大小一致，并与笔记模块位置规则一致；
9. 长文输入和流式输出达到性能阈值。
10. Typewriter 底部打字滑块远距离点击时从当前视觉位置连续过渡，无瞬移、回弹和明显卡顿。

### 7.2 发布阻断条件

以下任一项失败都不得生成安装包：

- 任何 Office provider 仍将 422 错误显示为网络错误；
- 工具消息字段在任一能力边界被剥离；
- 会话历史存在跨 scope 串台、丢消息或无法恢复；
- Dock 无法在真实安装版输入、发送、拖动、点击新建对话或打开会话历史；
- Typewriter 首屏仍出现编辑器空壳、工具栏延迟挂载或首次交互造成整棵组件树重渲染；
- Typewriter 图片仍出现在正文上方独立区域，或不能持久化尺寸/位置；
- 未完成 Windows 安装包、冷启动、升级、回滚和日志脱敏验收。
