# Friday Preview.22 问题分析与根因报告

**文档状态**：研究阶段冻结稿，尚未修改实现代码

**调查日期**：2026-10-30（Asia/Shanghai）

**调查范围**：Office Docs/Sheets/Slides/PDF 助手、主对话、笔记助手、知识库普通对话与 Agent 对话、日程助手、全局 Dock、Friday 设置、Typewriter 编辑与预览

**关联版本**：源码 `3.0.6-preview.21`，工作分支 `codex/friday-3.0.6-preview.8`

**本阶段结论**：不以“网络问题”解释全部失败；Office 422 已经定位到请求协议在 AI Core 能力边界被破坏。历史、浮层、输入与 Typewriter 图片问题属于独立的界面/数据边界问题，不能用 Office 重试或局部 CSS 修复替代。

## 1. 用户报告的可观察问题

### 1.1 Office 助手普遍报错

用户在 Docs、Slides 中均看到：

> 错误：模型请求失败（model_request，HTTP 422）

同一模型在主对话可用，Office 侧已选中 DeepSeek，但 Office 经过一次工具步骤后再次请求时失败。失败发生在模型已经收到第一轮请求、并准备处理工具结果的阶段，因此“检查本机网络”不能解释这一现象。

### 1.2 Office 历史与侧边栏遮挡

用户反馈 Office 的历史记录弹层被侧边栏边缘遮挡，部分入口的历史不能像 DeepSeek 一样选择某条会话并完整恢复。Office 的上游 renderer 已有按文件列出聊天的能力，但它和 Friday 主应用的 `sessions/messages` 事实源、Dock 及笔记/日程浮层不是同一套 UI 合同。

### 1.3 笔记与日程助手缺少统一的新建入口

笔记助手和日程助手虽然都能打开历史按钮，但视觉、位置、输入布局和新建会话行为不同。用户要求所有 AI 对话窗口统一为悬浮侧边栏，并且每个窗口都有同样的新建对话按钮、搜索、选择、恢复和续聊动作。

### 1.4 Dock 交互和视觉不一致

用户报告 Dock 在 Office 中遮挡内容、拖动无效或拖动范围不正确、展开卡顿、输入框缺失/无法发送、历史区域与其他对话窗口不一致。

当前源码已经包含 Dock 输入框和 `friday-dock` 作用域，但这只说明开发版本具备局部实现，不代表实际安装包的事件、焦点、模型配置同步和 Office overlay 均已通过完整验收。当前 Dock 的 `officeOverlay` 分支直接使用主进程 `office-dock-move` 和固定右下角布局，属于第二套坐标与层级系统，是遮挡和拖动问题的高风险来源。

#### 1.4.1 Dock 控件没有遵循统一按钮合同

Dock 的“新建对话”和“会话历史”不能只是面板里的文字入口或依赖某个局部图标；它们应当是与主对话、Office、笔记、知识库和日程完全同构的按钮组件，拥有相同的图标语义、按钮尺寸、hover/pressed/disabled/focus 状态、无障碍标签和事件合同。当前缺少这种统一合同时，会出现按钮不显示、点击区域不一致、打开了错误 scope、历史侧栏无法恢复或新建后仍复用旧会话的问题。根因是 Dock 自己维护展开状态和会话状态，没有复用各模块的 `HistoryButton`/`NewConversation` 入口协议，而不是单纯缺少一段模板或 CSS。

### 1.5 Typewriter 输入卡顿、图片位置错误

用户要求：

1. 长文输入保持流畅；
2. 图片显示在纸张正文中，而不是正文上方的独立图片条；
3. 图片默认小图，可用鼠标拖拽缩放；
4. 图片与纸张材质、灯光、阴影融合。

当前实现把图片从 Markdown 中扫描出来后渲染到 `typewriter-image-strip`，正文编辑器仍是 `<textarea>`，因此编辑区没有图片节点、没有图片尺寸状态，也没有拖拽缩放目标。预览模式虽然通过 `v-html` 渲染图片，但只设置 `max-width: 100%` 和固定阴影，不能把图片尺寸写回文档，也没有纸张光照模型的联动。

用户进一步要求 Typewriter 的组件尽量一次性加载出来。现状的问题不是简单的“是否使用懒加载”，而是编辑器外壳、正文渲染器、图片节点、工具栏和预览资源没有明确的加载优先级与预热合同：如果组件按页面交互临时加载，用户会先看到空壳、延迟出现的工具栏或图片占位，随后又触发整棵组件树重渲染。根因是没有定义“首屏可交互核心组件必须就绪、重资源可以后台预热”的加载边界，也没有用真实设备测量加载期间的主线程阻塞和布局跳变。

### 1.6 Typewriter 打字滑块的瞬移与物理过渡问题

用户补充：当底部打字滑块处于静止状态，点击远处文字位置时，滑块应沿轨道丝滑移动到对应位置，而不是直接跳到目标坐标。该现象属于编辑器对“选区/光标位置变化”与“视觉滑块位置”之间缺少动画状态机的问题。当前若直接把 DOM 的 `left`/`transform` 绑定到新测量值，浏览器只会提交一次最终布局，用户看到的是瞬移；如果在长文中每个输入事件都重新测量并强行过渡，又会导致动画追赶、抖动或输入卡顿。

根因需要从三层确认：目标位置测量是否稳定、滑块是否拥有独立的 previous/target 状态、动画是否能在新点击到来时取消并从当前视觉位置平滑追赶。还需遵守 `prefers-reduced-motion`，并保证动画不改变真实光标/选区和键盘输入语义。

1. 在 Friday 设置中配置一个可用的 DeepSeek API Key、`deepseek-flash` 和 `https://api.deepseek.com`。

## 3. 根因分析

### 3.1 P0：AI Core schema 破坏了 OpenAI 工具调用协议

Office 的实际数据流是：

```text
AgentMessage[]
  → office-ai-bridge.toOpenAiMessages()
  → createAiChatCapabilityInvoker()
  → executeCapability('ai_chat_inference')
  → aiChat.schema.safeParse()
  → handler(ctx.chat(parsed.data))
  → fridayStreamRequest()
  → DeepSeek /chat/completions
```

第一轮消息通常只有 `system` 和 `user`，`role/content` 足够，所以请求可能成功。工具循环的第二轮至少包含：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_123",
      "type": "function",
      "function": {"name": "office_read", "arguments": "{}"}
    }
  ]
}
{
  "role": "tool",
  "tool_call_id": "call_123",
  "content": "..."
}
```

但 `z.object({ role, content })` 会得到：

```json
{
  "role": "assistant",
  "content": null
}
{
  "role": "tool",
  "content": "..."
}
```

`tool_call_id` 是 OpenAI-compatible API 对 tool 消息的必需字段。DeepSeek 在消息反序列化阶段拒绝请求，返回 422。重试无法修复一个稳定的错误 payload；继续增加重试只会放大用户的等待和错误次数。

### 3.2 P0/P1：DeepSeek thinking 与工具循环的协议不完整

上游 `vendor/happyoffice/packages/ai-provider/src/registry.ts:65-82` 已明确写出：DeepSeek V4/Flash 在 thinking 开启时，后续工具轮必须回传上一轮的 `reasoning_content`。当前 Office bridge：

1. 只把流中的 reasoning 片段推送给 renderer；
2. `toOpenAiMessages()` 不把 `m.reasoning` 转为 `reasoning_content`；
3. `aiChat` schema 也不允许扩展字段；
4. 上游 AgentLoop 在新 run 开始时会清除已结束 assistant 的 reasoning（`vendor/happyoffice/packages/agent-core/src/loop.ts:313-334`）。

因此，即使只修复 `tool_call_id`，在开启 thinking 的 DeepSeek V4/Flash 工具续轮中仍存在第二个协议失败点。研究阶段应先把它作为独立门禁，而不是假设一次 schema 修改就能证明 Office 已稳定。

### 3.3 P1：错误分类和用户文案在边界处失真

`src-electron/ai-core/network-policy.js:107-134` 的设计目标是避免 API Key 和响应正文泄露，但 `annotateNetworkError()` 会把 provider 原始错误覆盖成安全摘要，`fridayStreamRequest()` 对非 2xx 又主动取消 response body。结果是：

- 日志可以留下 `model_request`，但没有 `status/param/provider code` 的可读摘要；
- renderer 只能显示“模型请求失败”或“网络有问题”；
- 用户明明连接着 DeepSeek，却被要求检查网络；
- 调试无法快速区分 401、模型名错误、422 参数错误和网络断开。

正确的设计应是“脱敏但保留结构化错误”：`classification`、HTTP 状态、provider code、param、requestId、可操作建议；不保存 API Key、消息正文或完整响应。

### 3.4 P1：六类对话没有统一的事实源和浮层合同

当前实现同时存在：

- Friday 主应用的 SQLite `sessions/messages` 与 `scope/scopeKey`；
- Office vendor ProjectStore 的 `projectId/chatId`、按文件绑定的 JSONL；
- 日程独立的卡片式 `historyMessages`；
- 笔记侧边栏的 AI 消息数组与 scoped session；
- 知识库普通/Agent 两套对话组件；
- Dock 独立的 `friday-dock` scope。

`ScopedHistoryButton.vue` 能把部分入口的列表和读取动作统一，但它只处理历史按钮，不统一聊天面板、输入、空态、浮层定位和焦点。日程 `FridayAssistant.vue` 仍把历史消息渲染在卡片内部；笔记 `NoteEditor.vue` 使用固定宽度的编辑器侧栏；知识库使用独立 Teleport 对话框；Office 使用 vendor 自己的侧边栏。

这会产生四类结构性缺陷：

1. 同一会话在不同入口的标题、时间、搜索和新建行为不一致；
2. 浮层受父级 `overflow`、`z-index` 和编辑器 WebContentsView 边界影响；
3. 选择历史后各组件自行处理异步恢复，快速连续点击可能出现旧请求覆盖新选择；
4. Office 文件会话与 Friday scope 没有统一的迁移和审计合同。

### 3.5 P1：Office overlay 使用第二套坐标和遮挡模型

`GlobalAgentDock.vue:173-176` 在 `officeOverlay` 下不使用普通 Dock 的位置样式，`moveDrag()` 在 `316-323` 改为向主进程发送增量移动，CSS 在 `529-534` 将面板固定到右下角并贴边。Office 自己还有 AI panel 的 side preference、panel width、history popover 和 WebContentsView 布局。

两套系统同时存在时，任何一侧的宽度、缩放、标题栏高度或侧栏边界变化都可能造成：

- 历史弹层被 Office 面板边缘裁剪；
- Dock 面板覆盖编辑器输入区；
- 拖动起点和实际窗口坐标不一致；
- 展开时主进程重新计算 overlay bounds，用户感知为卡顿；
- panel 获得焦点后，编辑器不能再输入。

### 3.6 P1：Typewriter 的正文模型不支持图片节点

`src/features/typewriter/plugins/NoteSurface.tsx` 使用 `<textarea>` 保存纯文本 Markdown，所有正文输入通过 `onChange` 传给 `createNoteDocument().change()`。textarea 无法承载可交互的图片 DOM 节点，因此图片只能通过 `TypewriterView.vue:33-39` 从文本扫描后放到 `typewriter-image-strip`。

同时，当前链路有三个性能热点：

1. `handleSourceChange()` 每次输入都会安排图片扫描；长文扫描是完整 Markdown 正则遍历；
2. 预览通过 `markdownToNote()`、`DOMParser` 和 `v-html` 重建整段 HTML；
3. Nocturne stage 持续维护多个 canvas、光照和光标层，textarea 输入还要触发镜像、光标测量和 selection 事件。

已有代码对超过 20,000 字符启用 `wrap=off`、`requestAnimationFrame` 和延迟镜像，这是局部优化，但无法解决“图片不是正文节点”和“预览/扫描仍是全量转换”的结构限制。

### 3.7 P2：设置中的 Agent 选择没有后端路由合同

`src-electron/types.js` 明确注释：`globalAgentDock.agentId/mode` 在 chat runtime 暴露 agent-aware contract 前只是 UI preference。`SettingsGeneral.vue` 可以保存 Friday、Researcher、Auto，但 Dock 发送仍调用统一的 `chat_with_memory`，UI 选择不能证明后端实际切换 Agent。必须在 PRD 中把真实能力和展示语义分开，避免伪造切换效果。

## 6. 根因结论

Office 错误的第一根因是 AI Core 的私有模型推理能力错误地使用了会剥离未知字段的普通 Zod object，破坏了 OpenAI tool-call transcript；第二根因是 DeepSeek thinking 的 reasoning round-trip 没有合同；第三根因是错误脱敏策略丢失了对用户有用的参数错误信息。

全局体验问题的共同根因不是某个按钮少了，而是对话事实源、浮层渲染层、资源范围和输入生命周期没有统一抽象：每个入口都能“局部显示聊天”，但没有共享同一套会话、浮层、焦点和恢复协议。

Typewriter 图片问题的根因是编辑器仍是纯文本 textarea，而用户需求已经变成了带图片节点和布局元数据的文档编辑器需求；继续在图片条上增加 CSS 或继续扫描 Markdown，无法从根上满足正文内拖拽缩放和纸张光照融合。

Typewriter 加载问题的根因是缺少组件加载分层和预热协议：核心编辑能力没有作为首屏就绪集合，重资源又没有统一的后台预取策略。Dock 按钮问题的根因是没有共享统一的历史/新建按钮合同和 scope 传递协议；修补一个图标或增加一次点击监听，无法保证六类入口的语义一致。
