# Friday 下一版 AI HTML 融合研究与实施方案

日期：2026-11-06｜状态：研究及规划，待目标版本冻结与评审｜适用对象：产品、研发、测试、发布与维护负责人

## 1. 结论和决策

下一版的目标是在 Friday Office 内接入 GenOffice 的 **完整 AI HTML 应用**，让用户能够新建或打开 `.html/.htm`，编辑源代码、可视化编辑和实时预览，通过 AI 规划、生成、修改页面，管理附件和图片，演示、保存、导出及打印。必须同时对接 Friday 的模型配置、文件权限、任务、标签页和宿主生命周期。仅能打开 HTML、只提供聊天生成代码，或把 HTML 作为普通笔记显示，都不满足需求。

建议采用“**固定上游版本 + 完整应用迁入 vendor + Friday 宿主适配层**”：保留上游 HTML 编辑模型、AI 工作流和运行所需共享包；通过清晰的主进程、preload 和服务接口接入 Friday；逐项记录与上游的差异；以受控开关和真实对照验收决定何时启用。不要直接修改 `resources/office` 的构建输出，也不要把 AI 功能重写成一批针对按钮的临时分支。

这里的方案是下一版研发合同，不代表当前已接入、已经验证或者已批准上游版本。用户要求“功能与 GenOffice 一致”意味着在**冻结的同版本、同平台、同输入和同服务可用条件下**，比较可见功能、文件效果、错误与取消；AI 生成的自然语言或页面不要求逐字一致。目标自身限制也要如实呈现，不凭空承诺超出上游的格式和保真度。

## 3. 原因研究：为什么不能只加一个按钮

1. **编辑器本身尚未启用。** `src-electron/office/editor-registry.js` 将 HTML 标为 `enabled: false`，原因 `FULL_APP_PARITY_PENDING`；文件类型、标签、宿主 view 和打包链也有独立的四编辑器分支。仅改 registry 会出现入口和实际加载不一致。
2. **AI 模型是能力的一部分，不是业务执行器。** 上游 HTML 面板在 renderer 中维护文档上下文和工具执行，再通过 preload 和 IPC 调用模型流；Friday 的模型桥能处理部分文字模型流，不代表文档应用、资源、搜索和文件交付已经接好。HTML 面板工具也不自动成为 Friday 主助手工具。
3. **完整页面有状态及副作用。** HTML 的源码是主要真相；预览中的 DOM、人工修改、AI 异步操作、图片下载和保存必须对同一文档及版本生效。单纯发送一段聊天回答不能保证写入源文件，也无法正确处理撤销、冲突与取消。
4. **外部服务当前存在真实缺口。** `src-electron/office/office-ai-bridge.js` 当前搜索返回空数组、下载图片返回 null、图像能力返回不可用；候选 HTML 还有模块自有图片 IPC，不能只替换一个公共处理器。空结果、未配置、网络错误和真正成功应区分。
5. **HTML 是可执行内容。** 上游预览允许脚本、表单和弹窗等，以便保持交互；因此还必须确保网页不能获得 Friday 的 Node、preload、模型密钥或任意文件权限，不能简单地将全部脚本关闭后声称与上游一致。
6. **旧版与候选不是同一份代码。** 已比较的关键 HTML 文件在当前 vendor 与 `.852` 候选之间不同；候选工具中包含 `search_images`、`generate_image`，不能用当前 vendor 工具列表推断目标完整能力。应在冻结目标后重新盘点所有菜单、工具、快捷键和 IPC。

## 4. 用户能完成什么

完整用户旅程：新建或选择本地 `.html/.htm` → 进入专用 HTML 编辑器 → 通过源码、预览或可视方式查看和修改 → 选中局部向 AI 提问或让 AI 澄清、规划并生成页面 → 按需求添加附件、图片及外部资料 → 审阅页面与 AI 改动 → 保存、另存或演示 → 必要时导出 PDF、DOCX、单文件 HTML 或打印。

入口需覆盖新建、现有文件明确选择“用 AI HTML 编辑”、多标签与最近文件；保留原 HTML 查看器及原有打开偏好，不以隐式导入、同名匹配或自动覆盖改变用户数据。首次保存、另存、重命名和磁盘外部修改都要保持文件、图片资产及项目聊天身份正确。主助手的接入按技术文档给出的操作目录和授权合同实施，不能把编辑器内 AI 自动冒称主助手可执行。

## 6. 推荐架构及关键设计

```text
Friday 工作区 / 文件入口 / 主助手
       ↓ 活跃文档、权限、能力与任务
Friday Office 宿主 / HTML adapter / AI 服务与交付
       ↓ 版本化接口、IPC、流与资源协议
GenOffice HTML main + preload + renderer + 共享包
       ↓ source / 结构化 ops / 受隔离预览
HTML 文档、受授权资产和已验证导出文件
```

**边界与职责：** 上游负责页面源码模型、预览、交互和 HTML 应用内 AI 工作流；Friday 负责真实文件授权、标签/窗口、模型设置、安全服务、任务与审计、构建分发。接入优先通过通用配置接口及薄 adapter；确需修改 vendor 的通用 hook 必须进入差异账本并定义上游消化后的删除条件。宿主不可直接引用构建产物作为修复源。

**版本和一致性：** 文档 session、owner、文件身份及 revision 随所有异步请求传播。AI 操作提交前再次核对当前文档与版本；本地手改、切标签、关闭、Stop 或附件下载结束之后的迟到结果不能覆盖新内容。整批编辑要么全部应用，要么不应用。保存与导出以明确的快照为基础，分开报告生成成功和打开成功。

**多入口一致性：** 原上游 HTML 面板沿用其工具体验；Friday 主助手通过可查询的领域能力和授权操作接入对应文档，不绕过上述同一源模型。人工菜单、编辑器 AI 和主助手对同类副作用应共享资源、权限、错误和任务合同，不要求三个入口在首版具备相同的对话 UI。

**服务可用性：** 文本模型、搜索、图片搜索和图片生成按 provider、凭据、网络与模型特性独立探测。启用真实 provider 后，在与上游相同条件下完成对应能力；缺配置时提示具体原因，不能将占位结果标为成功，也不能把缺服务作为完整对等已通过。密钥继续保存在 Friday 配置体系，禁止为兼容上游写入额外明文密钥副本。

**安全与保真：** iframe 保留上游合法交互，同时独立验证 sender、协议、文档与资产授权、消息来源、外链、跳转、网络访问、重定向和资源清理。远程资源可能带来隐私与数据外传风险，要明确披露并设计可执行的网络策略；有必要收紧行为时应记录与上游差异，验证原有合法交互而不是静默破坏。

## 7. 关键技术难点与处理

| 难点 | 方案与判定 |
| --- | --- |
| 上游依赖闭包和版本漂移 | 固定上游提交并比较 HTML、共享包、lockfile、构建、许可证及 Electron 兼容；在隔离集成分支评估整体升级与选择性迁入。未经依赖和回归证据不得宣布可用。 |
| HTML 与 Friday 数据身份不同 | 以文档 session 和规范化路径而非文件名绑定；首存、另存、rename 明确聊天和资源归属；dirty 与外部修改冲突必须有用户决策和恢复证据。 |
| 异步 AI 与人同时修改 | revision/stale guard、批处理原子、受控队列、取消传播和晚到响应拒绝；附件或图片异步结束后再次验证。 |
| 预览执行代码又需隔离 | 隔离预览来源与宿主桥、最小协议资源权限、受控导航/网络/弹窗；对脚本交互和恶意页面分别实测。上游目录授权范围不能自动等于 sender 级隔离。候选的 inspector 协议说明页面脚本与 inspector 可来自同一个 iframe；`event.source` 只能确认 iframe，不能鉴别发信脚本。须研究并验证可伪造编辑消息的风险，不能把该检查当作可信写入授权。 |
| 媒体与搜索服务合同不同 | 分离 web 的 `results`、图片搜索的 `images`、生成图片的 `url/error`；验证真零结果、错误、取消、落盘；审计远程抓取的内网、重定向和 DNS 重绑定。 |
| 图片资产随文档迁移 | 明确文档资产根、临时资产和引用清单；另存跨目录时事务化复制/重写、失败回滚，避免删掉其他文档引用的文件。 |
| 全页、打印和导出的能力不同 | 按 GUI 和 headless 各自验收文件；单文件 HTML 对跳过资源报告，PDF/打印脚本行为分别验证，DOCX 不承诺任意 CSS 完美还原。 |
| 既有 PDF 修复和上游更新相互影响 | 保留 preview.36 当前工作区与 vendor 差异，先固定可拉取基线及其证据；新集成不得丢弃已有 PDF→Word 改动或假定尚未关闭的验收已经通过。 |

## 9. 验收和发布门槛

- **参考与候选可重放：** 固定目标、源提交、vendor commit、dirty 状态、依赖锁摘要、系统、样本哈希、服务配置标识和构建包摘要；不记录密钥或原始敏感文件。
- **功能对等：** 每个上游入口和工具有台账及 Friday 对应项；目标实际运行与 Friday 最终安装包在相同条件下分别记录，所有 P0 子项通过，不将自动 fixture 代替人工关键流程。
- **真实产物：** 直接打开保存的 `.html/.htm` 与导出 PDF/DOCX；检查内容、资源和结构；记录源和目标保存前后哈希、可打开状态和允许的变化。正常保存本来允许改变源文件。
- **安全与可靠性：** 运行恶意 HTML、跨标签 IPC、路径穿越、符号链接/Windows junction、远程重定向、敏感信息、Stop、崩溃、取消、只读、占用、另存失败和外部变更等负向案例。
- **安装与回归：** 无源码干净安装、旧版升级、用户数据和聊天保存、回滚、卸载重装，以及 PDF→Word 和 docs/sheets/slides/pdf 既有主要流程；性能预算和复杂页面样本在 G0 冻结并实测。
- **发布声明：** 明确目标上游版本、实际功能及已知限制；安装器、源与构建证明匹配；签名、许可及公开发布流程依项目发布合同处理。草稿、安装器存在和公开发布是不同状态。

## 10. 跟随 GenOffice 后续更新

遵循既有 Office 上游合同 U0–U5：观察并固定目标 → 三方差异与许可审计 → 在独立集成环境移植 → 干净构建和合同测试 → 完整功能对照 → 安装升级与整套回滚。HTML 的子项台账要跟随上游每次变更更新，新增菜单、工具、IPC 或资源协议自动进入待映射状态；不是只看 tag 或是否能编译。来源、patch、实际报告、目标身份和包摘要要相互校验，不能只手填“通过”。
